# Архітектурні рішення

Записи мають автора, дату, проблему, варіанти, рішення та наслідки.

## D-3-001 — Фіксація .NET 10

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Розробники та CI можуть використовувати різні SDK.
- Розглянуті варіанти: Локальна версія без фіксації; global.json.
- Рішення: global.json задає 10.0.300, rollForward latestFeature; усі бібліотеки використовують net10.0.
- Наслідки: CI встановлює сумісний .NET 10 SDK; інші major-версії не вибираються.

## D-3-002 — Central Package Management

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Шаблони мають різні версії NuGet-пакетів.
- Розглянуті варіанти: Версії в кожному csproj; спільний файл версій.
- Рішення: Усі PackageReference без Version; версії у Directory.Packages.props. Logging.Debug узгоджено з Hosting 10.0.8.
- Наслідки: Зміна версії пакета однакова для всього solution; NuGet виявляє конфлікти.

## D-3-003 — CI-фільтр та Windows-збірка

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: MAUI потребує платформних workloads і не входить до Linux-збірки.
- Розглянуті варіанти: Один runner для всього; окремі jobs.
- Рішення: Microclimate.Ci.slnf містить усі 10 проєктів, крім MAUI; Windows збирає MAUI окремо з явно обмеженим TargetFrameworks.
- Наслідки: Linux перевіряє сервер і тести без Android/Apple SDK; Windows не відновлює інші платформи.

## D-3-004 — Попередження MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Стандартний MAUI-шаблон і платформні generators можуть мати попередження.
- Розглянуті варіанти: Зупиняти всі збірки; тимчасовий виняток для MAUI.
- Рішення: TreatWarningsAsErrors=true спільно; лише MAUI задає false. XAML compiled bindings залишаються строгими.
- Наслідки: На Етапі 1 Учасник 3 має усунути попередження й повернути true; це не дозвіл ігнорувати помилки.

## D-3-005 — Платформи MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Потрібні Android і Windows; розробка відбувається на macOS.
- Розглянуті варіанти: Лише обов’язкові платформи; додати Apple-платформи на Mac.
- Рішення: Android доступний завжди; Windows додається на Windows; iOS і MacCatalyst — тільки на macOS.
- Наслідки: Windows CI і README обмежують відновлення конкретним TFM; MacCatalyst придатний для локальної перевірки навігації.

## D-3-006 — Формат solution та спільний TFM

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Шаблон .NET 10 створює slnx; спільний TargetFramework може конфліктувати з multi-targeting MAUI.
- Розглянуті варіанти: Старий sln; slnx. Безумовний TFM; умовне задання.

## D-3-007 — Тести клієнта на Linux

- Дата: 2026-10-12

## D-3-008 — Виправлена транзитивна OpenAPI-залежність

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: NuGet Audit відхилив Microsoft.OpenApi 2.0.0 з шаблону через GHSA-v5pm-xwqc-g5wc.
- Розглянуті варіанти: Вимкнути audit; оновити залежність.

- Наслідки: Restore має проходити з виправленою бібліотекою; джерело: https://github.com/advisories/GHSA-v5pm-xwqc-g5wc.

## D-3-009 — Точна назва тестової заглушки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Завдання вимагає Placeholder_ShouldPass, а CA1707 забороняє underscore у публічних іменах.
- Розглянуті варіанти: Змінити задану назву; точкове обґрунтоване приглушення.
- Рішення: Лише методи Placeholder_ShouldPass мають SuppressMessage CA1707 із поясненням; правило для іншого коду не змінюється.
- Наслідки: Після заміни заглушок реальними тестами прибрати виняток. Збірка решти коду залишається строгою.


## D-3-010 — Вибір платформи тільки для клієнта

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: глобальна CLI-властивість TargetFrameworks поширюється на Contracts під час restore і змінює її платформонезалежний target.
- Розглянуті варіанти: глобальний TargetFrameworks; окрема властивість тільки клієнта.

- Наслідки: Contracts залишається net10.0; відновлення клієнта не вимагає workloads інших платформ.

## D-3-011 — Стабільний Apple SDK і межі локальної перевірки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: встановлено Xcode 27.0 (27A266a), а стабільний MacCatalyst SDK 26.5.10315 вимагає Xcode 26.6. Preview SDK 27 компілює C#/XAML, але native linker не знаходить EnhancedLinkSecurity.
- Розглянуті варіанти: заміна глобального Xcode; preview SDK; залишити стабільні targets і задекларувати блокер.
- Рішення: не змінювати Xcode, який потрібний іншим проєктам; залишити шаблонні Apple targets і мінімальну версію 15.0, не додавати preview opt-in до фінального проєкту. README дає Mac-команди для сумісного Xcode 26.6.
- Наслідки: локальний запуск Mac не підтверджено. Windows-збірку перевіряє CI; ручний Windows-запуск залишається командною перевіркою.

## D-3-012 — Залежні PR без прямої зміни main

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: наступні кроки потребують каркасу до завершення людського рев’ю першого PR.
- Розглянуті варіанти: чекати merge після кожного кроку; послідовні залежні гілки.
- Рішення: кожен issue має feature-гілку та PR у main; наступна гілка містить попередні кроки. Людина переглядає й зливає A→B→C→D→E→F→G через merge commit.
- Наслідки: робота повністю підготовлена до рев’ю; main і статуси issues не змінюються до merge. Після кожного попереднього merge diff наступного PR скорочується.

## D-2-001 — Controllers замість Minimal API

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Вибір архітектурного підходу до реалізації HTTP API (Controllers проти Minimal APIs) для комплексної системи з багатьма ресурсами, версіонуванням та авторизацією.
- Розглянуті варіанти: Minimal APIs; Controller-based підхід (`ControllerBase`).
- Рішення: Використовувати класичні ASP.NET Core Controllers (`[ApiController]`).
- Наслідки: Чітка структуризація ендпоінтів за бізнес-ресурсами у папках контролерів; зручна декларативна фільтрація атрибутами (`[Authorize(Roles = "...")]`, `[ApiVersion]`, `[ProducesResponseType]`); автоматична інтеграція валідації моделі та легке генерування OpenAPI-документації за версіями.

## D-2-002 — Версіонування API через сегмент URL (/api/v1)

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Вибір способу передачі версії API між клієнтом і сервером.
- Розглянуті варіанти: Кастомний заголовок (`X-Api-Version`); query-параметр (`?api-version=1.0`); сегмент URL шляху (`/api/v1/...`).
- Рішення: Використовувати `UrlSegmentApiVersionReader` із префіксом `/api/v{version:apiVersion}/`.
- Наслідки: Версія є явною та видимою в маршруті, що спрощує кешування на рівні HTTP-проксі, тестування в Postman/Swagger та маршрутизацію запитів у кросплатформеному клієнті .NET MAUI. Непідтримувані версії автоматично повертають помилку версіонування.

## D-2-003 — Вбудований OpenAPI .NET 10 + Asp.Versioning.OpenApi + Swagger UI

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Інструмент генерації документації OpenAPI та UI-інтерфейсу в середовищі .NET 10.
- Розглянуті варіанти: Застарілий повний `Swashbuckle.AspNetCore`; `Scalar.AspNetCore`; вбудований у .NET 10 пакет `Microsoft.AspNetCore.OpenApi` разом з `Asp.Versioning.OpenApi` та `Swashbuckle.AspNetCore.SwaggerUI`.
- Рішення: Використовувати нативну генерацію специфікації `Microsoft.AspNetCore.OpenApi` через source-генератори .NET 10, інтеграцію версій через `Asp.Versioning.OpenApi`, а Swagger UI підключати виключно як статичний рендерер UI (`UseSwaggerUI`).
- Наслідки: Відсутність застарілих рефлексивних фільтрів старого Swashbuckle, висока швидкодія компіляції та відповідність найновішим рекомендаціям платформи .NET 10.

## D-2-004 — Відокремлений шар Contracts без залежності від Domain

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Залежності між клієнтом і сервером; ризик витоку внутрішніх сутностей предметної області в публічний API (Domain entities leakage).
- Розглянуті варіанти: Спільне посилання клієнта на Domain; єдиний проєкт спільних типів; ізольована бібліотека `Microclimate.Contracts`.
- Рішення: Створити чисту бібліотеку `Microclimate.Contracts`, що не має посилань на жодні інші проєкти рішення чи сторонні важкі пакети. Усі DTO реалізовані як `public sealed record`. Публічні enum-и (`MetricType`, `AlertLevel`, `UserRole`) визначені в Contracts, а шар Application/Api відповідає за мапінг між внутрішніми моделями Domain та зовнішніми контрактами.
- Наслідки: Клієнт (`Client.Maui`) не тягне важкі залежності домену, бізнес-правил чи EF Core; зміни внутрішньої БД не ламають публічний контракт; висока швидкість збірки без попереджень.

## D-2-005 — Аутентифікація JWT з ротацією refresh-токенів та PasswordHasher

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Механізм автентифікації користувачів і сесій для багатокористувацької кросплатформеної системи.
- Розглянуті варіанти: Важкий фреймворк ASP.NET Core Identity з повною схемою БД; легковажна кастомна модель на JWT + `PasswordHasher<TUser>`.
- Рішення: Короткоживучі JWT access-токени (15 хвилин) з підписом HMAC-SHA256 та криптографічні випадкові refresh-токени (7 діб) з обов'язковою одноразовою ротацією при кожному оновленні. Для паролів використовується стандартний `PasswordHasher` (PBKDF2) з бібліотеки Identity без розгортання повної інфраструктури Identity.
- Наслідки: Мінімальне навантаження на базу даних, відсутність зайвих 7+ таблиць Identity; надійний захист від повторного використання токенів (reuse detection): перехоплення старого refresh-токена автоматично анулює весь ланцюг сесій користувача.

## D-2-006 — X-Device-Key для апаратних сенсорів замість JWT

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Спосіб автентифікації автономних IoT-датчиків і симулятора при надсиланні пакетів вимірів.
- Розглянуті варіанти: Виділення кожному датчику службового облікового запису користувача з JWT; HTTP-заголовок `X-Device-Key` із хешуванням на сервері.
- Рішення: Датчики автентифікуються простим заголовком `X-Device-Key`. Ключ генерується при реєстрації сенсора, повертається одноразово, а в базі зберігається лише незворотний криптографічний хеш SHA-256.
- Наслідки: Датчики не потребують логіну, пароля чи підтримки життєвого циклу refresh-токенів; низькі накладні витрати на передачу та перевірку запиту; можливість швидкої ротації ключа сенсора адміністратором.

## D-2-007 — Уніфікований формат помилок RFC 9457 ProblemDetails

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Неоднорідні формати помилок у різних ендпоінтах ускладнюють обробку на стороні клієнта.
- Розглянуті варіанти: Кастомний JSON-об'єкт `{ success: false, error: "..." }`; стандартний RFC 9457 `application/problem+json`.
- Рішення: Усі помилки (помилки валідації 400, 401, 403, 404, 409, 413, 500) повертаються виключно у форматі `ProblemDetails` / `ValidationProblemDetails` через `GlobalExceptionHandler` (`IExceptionHandler`) та `builder.Services.AddProblemDetails()`.
- Наслідки: Кожна помилка містить уніфікований `type`, `title`, `status`, `instance` та `traceId` для трасування з логами OpenTelemetry. У Production чутливі деталі стека викликів автоматично приховуються від користувача.

## D-2-008 — Сповіщення в реальному часі через SignalR з групами за кімнатами

- Дата: 2026-10-12
- Автор: Учасник 2
- Проблема: Як сповіщати операторів та користувачів про перевищення порогів мікроклімату без постійного спаму запитами (polling).
- Розглянуті варіанти: Періодичні HTTP GET запити кожні кілька секунд (polling); WebSockets / ASP.NET Core SignalR.
- Рішення: Використовувати SignalR-хаб `/hubs/alerts` із груповою моделлю підписок (`room-{roomId}` для відкритих екранів та `all-alerts` для персоналу).
- Наслідки: Миттєва доставка подій `AlertRaised` та `MeasurementReceived` без зайвого мережевого трафіку. Підтримка автоматичного перепідключення (`WithAutomaticReconnect`) на стороні .NET MAUI клієнта.
