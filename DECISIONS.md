# Архітектурні рішення

Записи мають автора, дату, проблему, варіанти, рішення та наслідки.

## D-3-001 — Фіксація .NET 10

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Розробники та CI можуть використовувати різні SDK.
- Розглянуті варіанти: Локальна версія без фіксації; global.json.
- Рішення: global.json задає 10.0.300, rollForward latestFeature; усі бібліотеки використовують net10.0.
- Наслідки: CI встановлює сумісний .NET 10 SDK; інші major-версії не вибираються.

## D-3-002 — Central Package Management

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Шаблони мають різні версії NuGet-пакетів.
- Розглянуті варіанти: Версії в кожному csproj; спільний файл версій.
- Рішення: Усі PackageReference без Version; версії у Directory.Packages.props. Logging.Debug узгоджено з Hosting 10.0.8.
- Наслідки: Зміна версії пакета однакова для всього solution; NuGet виявляє конфлікти.

## D-3-003 — CI-фільтр та Windows-збірка

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: MAUI потребує платформних workloads і не входить до Linux-збірки.
- Розглянуті варіанти: Один runner для всього; окремі jobs.
- Рішення: Microclimate.Ci.slnf містить усі 10 проєктів, крім MAUI; Windows збирає MAUI окремо з явно обмеженим TargetFrameworks.
- Наслідки: Linux перевіряє сервер і тести без Android/Apple SDK; Windows не відновлює інші платформи.

## D-3-004 — Попередження MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Стандартний MAUI-шаблон і платформні generators можуть мати попередження.
- Розглянуті варіанти: Зупиняти всі збірки; тимчасовий виняток для MAUI.
- Рішення: TreatWarningsAsErrors=true спільно; лише MAUI задає false. XAML compiled bindings залишаються строгими.
- Наслідки: На Етапі 1 Учасник 3 має усунути попередження й повернути true; це не дозвіл ігнорувати помилки.

## D-3-005 — Платформи MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Потрібні Android і Windows; розробка відбувається на macOS.
- Розглянуті варіанти: Лише обов’язкові платформи; додати Apple-платформи на Mac.
- Рішення: Android доступний завжди; Windows додається на Windows; iOS і MacCatalyst — тільки на macOS.
- Наслідки: Windows CI і README обмежують відновлення конкретним TFM; MacCatalyst придатний для локальної перевірки навігації.

## D-3-006 — Формат solution та спільний TFM

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Шаблон .NET 10 створює slnx; спільний TargetFramework може конфліктувати з multi-targeting MAUI.
- Розглянуті варіанти: Старий sln; slnx. Безумовний TFM; умовне задання.
- Рішення: Зберігаємо Microclimate.slnx; Directory.Build.props задає net10.0 лише проєктам, назва яких не Microclimate.Client.Maui.
- Наслідки: MAUI має власні TargetFrameworks; slnf посилається на slnx, який підтримує сучасний MSBuild.

## D-3-007 — Тести клієнта на Linux

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: MAUI-проєкт неможливо використовувати як залежність звичайного Linux-тестового проєкту.
- Розглянуті варіанти: Посилання на MAUI; незалежний каркас тестів.
- Рішення: Client.Tests не посилається на MAUI; ViewModels тимчасово всередині клієнта.
- Наслідки: На Етапі 1 винести ViewModels/інтерфейси у платформонезалежну бібліотеку й додати реальні тести. Чотири поточні тести перевіряють лише запуск тестової інфраструктури.

## D-3-008 — Виправлена транзитивна OpenAPI-залежність

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: NuGet Audit відхилив Microsoft.OpenApi 2.0.0 з шаблону через GHSA-v5pm-xwqc-g5wc.
- Розглянуті варіанти: Вимкнути audit; оновити залежність.
- Рішення: CPM pinning фіксує Microsoft.OpenApi 2.7.5 у сумісній гілці 2.x; аудит і строгі попередження ввімкнені.
- Наслідки: Restore має проходити з виправленою бібліотекою; джерело: https://github.com/advisories/GHSA-v5pm-xwqc-g5wc.

## D-3-009 — Точна назва тестової заглушки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Завдання вимагає Placeholder_ShouldPass, а CA1707 забороняє underscore у публічних іменах.
- Розглянуті варіанти: Змінити задану назву; точкове обґрунтоване приглушення.
- Рішення: Лише методи Placeholder_ShouldPass мають SuppressMessage CA1707 із поясненням; правило для іншого коду не змінюється.
- Наслідки: Після заміни заглушок реальними тестами прибрати виняток. Збірка решти коду залишається строгою.


## D-3-010 — Вибір платформи тільки для клієнта

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: глобальна CLI-властивість TargetFrameworks поширюється на Contracts під час restore і змінює її платформонезалежний target.
- Розглянуті варіанти: глобальний TargetFrameworks; окрема властивість тільки клієнта.
- Рішення: MauiTargetFramework обмежує TargetFrameworks лише всередині MAUI csproj; CI і README використовують її. ProjectReference прибирає глобальні TargetFrameworks/RuntimeIdentifier під час build.
- Наслідки: Contracts залишається net10.0; відновлення клієнта не вимагає workloads інших платформ.

## D-3-011 — Стабільний Apple SDK і межі локальної перевірки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: встановлено Xcode 27.0 (27A266a), а стабільний MacCatalyst SDK 26.5.10315 вимагає Xcode 26.6. Preview SDK 27 компілює C#/XAML, але native linker не знаходить EnhancedLinkSecurity.
- Розглянуті варіанти: заміна глобального Xcode; preview SDK; залишити стабільні targets і задекларувати блокер.
- Рішення: не змінювати Xcode, який потрібний іншим проєктам; залишити шаблонні Apple targets і мінімальну версію 15.0, не додавати preview opt-in до фінального проєкту. README дає Mac-команди для сумісного Xcode 26.6.
- Наслідки: локальний запуск Mac не підтверджено. Windows-збірку перевіряє CI; ручний Windows-запуск залишається командною перевіркою.

## D-3-012 — Залежні PR без прямої зміни main

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: наступні кроки потребують каркасу до завершення людського рев’ю першого PR.
- Розглянуті варіанти: чекати merge після кожного кроку; послідовні залежні гілки.
- Рішення: кожен issue має feature-гілку та PR у main; наступна гілка містить попередні кроки. Людина переглядає й зливає A→B→C→D→E→F→G через merge commit.
- Наслідки: робота повністю підготовлена до рев’ю; main і статуси issues не змінюються до merge. Після кожного попереднього merge diff наступного PR скорочується.

## D-1-001 — Склад доменної моделі

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Які сутності й аналітичні функції входять у систему.
- Розглянуті варіанти: Модель з будівлями, refresh-токенами, пошуком аномалій та імпортом CSV; модель, що покриває вимоги ЛР1, критерію C5 і аналізу мікроклімату.
- Рішення: За погодженням з Учасником 2 модель містить кімнати, датчики, виміри, пороги, сповіщення й користувачів; аналітика — зведення за період, часовий ряд, індекс комфорту і сповіщення за порогами. Будівлі, refresh-токени, пошук аномалій та імпорт CSV до моделі не входять.
- Наслідки: Учаснику 2 потрібно прибрати з docs/api.md ендпоінти будівель, refresh і anomalies; Учаснику 3 — фільтр будівлі на Dashboard.

## D-1-002 — Кімната виміру через датчик

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Вимір прив'язаний до датчика, а датчик — до кімнати. Чи зберігати RoomId ще й у вимірі.
- Розглянуті варіанти: RoomId у Measurements; лише SensorId і JOIN із Sensors.
- Рішення: Лише SensorId. Датчики між кімнатами не переносяться, тож кімната виміру однозначно визначається датчиком.
- Наслідки: Схема в 3НФ без винятків. Запити за кімнатою роблять JOIN із Sensors; для швидкості є індекси Sensors(RoomId) і Measurements(SensorId, MetricType, MeasuredAt).

## D-1-003 — Enum-и в БД як рядки

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як зберігати MetricType, AlertLevel, AlertStatus, UserRole, RoomType.
- Розглянуті варіанти: int; рядок.

## D-1-004 — Типи первинних ключів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Однаковий тип ключа для всіх таблиць чи різний.
- Розглянуті варіанти: int identity скрізь; Guid скрізь; Guid і bigint для вимірів.

## D-1-005 — SQLite і PostgreSQL з окремими міграціями

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: ЛР1 вимагає незалежності від СУБД.
- Розглянуті варіанти: Одна СУБД; дві з одним набором міграцій; дві з окремими наборами.
- Рішення: Провайдер вибирається в конфігурації (Database:Provider), міграції окремі для кожного провайдера.
- Наслідки: SQLite для розробки й тестів, PostgreSQL у Docker. Відмінності описано в docs/db-schema.md, розділ 6.

## D-1-006 — Окремі репозиторії замість generic

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як Application отримує дані, не знаючи про EF Core.
- Розглянуті варіанти: Generic IRepository<T>; DbContext у сервісах; окремий інтерфейс на сутність з потрібними методами.

- Наслідки: Усі запити видно в інтерфейсах, їх легко підмінити в тестах; агрегати гарантовано рахуються в БД.

## D-1-007 — Перевірки в сутностях

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Де перевіряти правила: межі значень, порядок порогів, переходи статусу сповіщення.
- Розглянуті варіанти: Перевірки в сервісах; перевірки в конструкторах і методах сутностей.
- Рішення: Сутності мають private set і фабричні методи, які кидають DomainException.
- Наслідки: Некоректний об'єкт неможливо створити; правила тестуються без БД. Приватні конструктори без параметрів залишено для EF Core.

## D-1-008 — Час як параметр

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: DateTime.UtcNow усередині коду заважає тестам.
- Розглянуті варіанти: Власний IClock; TimeProvider; час як параметр методу.
- Рішення: Доменні методи приймають DateTimeOffset now; сервіси отримують TimeProvider з DI (як у Api Учасника 2). Увесь час приводиться до UTC.
- Наслідки: Тести працюють з фіксованим часом без моків.

## D-1-009 — Індекс комфорту на основі порогів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як звести кілька метрик в одну оцінку комфорту.
- Розглянуті варіанти: PMV/PPD за ISO 7730 (потрібні швидкість повітря, одяг, активність); зважене середнє оцінок за порогами.
- Рішення: Оцінка 100 у межах Warning, лінійне зниження до 0 на межі Critical; ваги T 0.30, CO₂ 0.30, RH 0.20, PM2.5 0.20; критична метрика робить категорію «Некомфортно».
- Наслідки: Індекс узгоджений зі сповіщеннями і змінюється разом із порогами кімнати; формулу легко перевірити вручну (docs/analytics.md, 3.4).

## D-1-010 — Підкреслення в назвах тестів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Назви Method_Scenario_Expected порушують CA1707, а TreatWarningsAsErrors робить це помилкою збірки.
- Розглянуті варіанти: SuppressMessage на кожному тесті (як D-3-009); інші назви; вимкнути CA1707 лише в тестових проєктах.
- Рішення: Локальний .editorconfig у tests/Microclimate.Domain.Tests і tests/Microclimate.Application.Tests вимикає CA1707.
- Наслідки: Правило діє для всього робочого коду, а назви тестів читаються як опис поведінки.

## D-1-011 — Закриття сповіщення

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як уникнути дублікатів сповіщень і коли їх закривати.
- Розглянуті варіанти: Нове сповіщення на кожне перевищення; одне незакрите сповіщення на кімнату й метрику.
- Рішення: Для кімнати й метрики існує не більше одного незакритого сповіщення. Воно закривається, щойно значення повертається в норму; зміна рівня закриває старе й створює нове.
- Наслідки: Клієнт не отримує потік однакових подій. Якщо значення коливається біля межі, сповіщення може часто відкриватися й закриватися — для навчального проєкту це прийнятно.
