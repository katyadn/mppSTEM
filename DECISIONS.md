# Архітектурні рішення

Записи мають автора, дату, проблему, варіанти, рішення та наслідки.

## D-3-001 — Фіксація .NET 10

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Розробники та CI можуть використовувати різні SDK.
- Розглянуті варіанти: Локальна версія без фіксації; global.json.
- Рішення: global.json задає 10.0.300, rollForward latestFeature; усі бібліотеки використовують net10.0.
- Наслідки: CI встановлює сумісний .NET 10 SDK; інші major-версії не вибираються.

## D-3-002 — Central Package Management

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Шаблони мають різні версії NuGet-пакетів.
- Розглянуті варіанти: Версії в кожному csproj; спільний файл версій.
- Рішення: Усі PackageReference без Version; версії у Directory.Packages.props. Logging.Debug узгоджено з Hosting 10.0.8.
- Наслідки: Зміна версії пакета однакова для всього solution; NuGet виявляє конфлікти.

## D-3-003 — CI-фільтр та Windows-збірка

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: MAUI потребує платформних workloads і не входить до Linux-збірки.
- Розглянуті варіанти: Один runner для всього; окремі jobs.
- Рішення: Microclimate.Ci.slnf містить усі 10 проєктів, крім MAUI; Windows збирає MAUI окремо з явно обмеженим TargetFrameworks.
- Наслідки: Linux перевіряє сервер і тести без Android/Apple SDK; Windows не відновлює інші платформи.

## D-3-004 — Попередження MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Стандартний MAUI-шаблон і платформні generators можуть мати попередження.
- Розглянуті варіанти: Зупиняти всі збірки; тимчасовий виняток для MAUI.
- Рішення: TreatWarningsAsErrors=true спільно; лише MAUI задає false. XAML compiled bindings залишаються строгими.
- Наслідки: На Етапі 1 Учасник 3 має усунути попередження й повернути true; це не дозвіл ігнорувати помилки.

## D-3-005 — Платформи MAUI

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Потрібні Android і Windows; розробка відбувається на macOS.

- Наслідки: Windows CI і README обмежують відновлення конкретним TFM; MacCatalyst придатний для локальної перевірки навігації.

## D-3-006 — Формат solution та спільний TFM

## D-3-007 — Тести клієнта на Linux

## D-3-009 — Точна назва тестової заглушки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: Завдання вимагає Placeholder_ShouldPass, а CA1707 забороняє underscore у публічних іменах.
- Розглянуті варіанти: Змінити задану назву; точкове обґрунтоване приглушення.
- Рішення: Лише методи Placeholder_ShouldPass мають SuppressMessage CA1707 із поясненням; правило для іншого коду не змінюється.
- Наслідки: Після заміни заглушок реальними тестами прибрати виняток. Збірка решти коду залишається строгою.


## D-3-010 — Вибір платформи тільки для клієнта

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: глобальна CLI-властивість TargetFrameworks поширюється на Contracts під час restore і змінює її платформонезалежний target.

## D-3-011 — Стабільний Apple SDK і межі локальної перевірки

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: встановлено Xcode 27.0 (27A266a), а стабільний MacCatalyst SDK 26.5.10315 вимагає Xcode 26.6. Preview SDK 27 компілює C#/XAML, але native linker не знаходить EnhancedLinkSecurity.
- Розглянуті варіанти: заміна глобального Xcode; preview SDK; залишити стабільні targets і задекларувати блокер.
- Рішення: не змінювати Xcode, який потрібний іншим проєктам; залишити шаблонні Apple targets і мінімальну версію 15.0, не додавати preview opt-in до фінального проєкту. README дає Mac-команди для сумісного Xcode 26.6.
- Наслідки: локальний запуск Mac не підтверджено. Windows-збірку перевіряє CI; ручний Windows-запуск залишається командною перевіркою.

## D-3-012 — Залежні PR без прямої зміни main

- Дата: 2026-10-12
- Автор: Учасник 3
- Проблема: наступні кроки потребують каркасу до завершення людського рев’ю першого PR.
- Розглянуті варіанти: чекати merge після кожного кроку; послідовні залежні гілки.
- Рішення: кожен issue має feature-гілку та PR у main; наступна гілка містить попередні кроки. Людина переглядає й зливає A→B→C→D→E→F→G через merge commit.
- Наслідки: робота повністю підготовлена до рев’ю; main і статуси issues не змінюються до merge. Після кожного попереднього merge diff наступного PR скорочується.

## D-1-001 — RoomId у Measurements як історичний факт

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Вимір прив'язаний до датчика, а датчик — до кімнати. Чи зберігати RoomId у вимірі, якщо його можна отримати через Sensors?
- Розглянуті варіанти: Лише SensorId і JOIN із Sensors; SensorId + RoomId у вимірі.
- Рішення: Measurements містить і SensorId, і RoomId; RoomId береться з датчика в момент виміру й більше не змінюється.
- Наслідки: Перенесення датчика не переписує історію кімнат; 3НФ не порушується, бо RoomId залежить від виміру, а не транзитивно від поточного SensorId. Запити аналітики за кімнатою працюють по одному індексу без JOIN. Див. docs/db-schema.md, 5.2.

## D-1-002 — Enum-и в БД як рядки

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як зберігати MetricType, AlertLevel, AlertStatus, UserRole, RoomType.
- Розглянуті варіанти: int; рядок; окремі довідникові таблиці.
- Рішення: Рядок (varchar(16–32)) через HasConversion<string>() на Етапі 1.
- Наслідки: БД читабельна без коду, зміна порядку значень enum не ламає дані. Мінус — більший обсяг таблиці Measurements; прийнятно для обсягів проєкту (docs/db-schema.md, розділ 6).

## D-1-003 — Типи первинних ключів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Однаковий тип ключа для всіх таблиць або різний.
- Розглянуті варіанти: int identity скрізь; Guid скрізь; Guid + bigint для Measurements.
- Рішення: Guid версії 7 (Guid.CreateVersion7, упорядкований за часом) для всіх сутностей, bigint identity для Measurements.
- Наслідки: Id генерується в домені до збереження й не розкриває кількість записів; v7 зменшує фрагментацію індексу. Для найбільшої таблиці bigint удвічі менший за Guid у PK і кожному індексі.

## D-1-004 — SQLite і PostgreSQL з окремими міграціями

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Програма дисципліни вимагає незалежності від СУБД (ЛР1, результат 2.5).
- Розглянуті варіанти: Лише PostgreSQL; лише SQLite; обидві з одним набором міграцій; обидві з окремими наборами.
- Рішення: Провайдер вибирається конфігурацією Database:Provider; міграції генеруються окремо для кожного провайдера; SQLite — розробка й тести, PostgreSQL — Docker.
- Наслідки: Міграції містять провайдер-специфічний DDL, тому один набір неможливий. Відмінності (DateTimeOffset у SQLite, конкурентність, часткові індекси) вирішуються конфігурацією EF за провайдером — docs/db-schema.md, розділ 7.

## D-1-005 — Специфічні репозиторії замість generic

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як шар Application отримує дані, не знаючи про EF Core.
- Розглянуті варіанти: Generic IRepository<T> з Find(Expression); DbContext напряму в сервісах; окремий інтерфейс на агрегат із методами під конкретні запити.
- Рішення: Окремі інтерфейси (IRoomRepository, IMeasurementRepository тощо) з методами під потрібні запити; IQueryable назовні не віддається.
- Наслідки: Кожен запит видно в інтерфейсі, його легко оптимізувати й підмінити в тестах; агрегування гарантовано виконується в БД. Мінус — більше методів, деякі Add/Remove повторюються.

## D-1-006 — Rich domain model з інваріантами в сутностях

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Де перевіряти правила (межі значень, порядок порогів, переходи статусу alert-а).
- Розглянуті варіанти: Anemic model з валідацією в сервісах; інваріанти в конструкторах і методах сутностей.
- Рішення: Сутності мають private set, фабричні методи й методи зміни стану, що кидають DomainException.
- Наслідки: Некоректний об'єкт неможливо створити з жодного місця коду; правила покриті unit-тестами без БД. Приватні конструктори без параметрів залишено для EF Core.

## D-1-007 — TimeProvider і час як параметр

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: DateTime.UtcNow усередині коду робить тести недетермінованими.
- Розглянуті варіанти: Власний IClock; TimeProvider (.NET 8+); час як параметр методу.
- Рішення: Доменні методи приймають DateTimeOffset now; сервіси Application отримують TimeProvider з DI (так само, як Api Учасника 2). Увесь час нормалізується до UTC.
- Наслідки: Тести використовують фіксований час без моків; не потрібна власна абстракція.

## D-1-008 — Індекс комфорту на основі порогів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як звести кілька метрик в одну оцінку комфорту.
- Розглянуті варіанти: Окремі «оптимальні» діапазони для комфорту; PMV/PPD за ISO 7730 (потребує швидкості повітря, одягу, активності); зважена сума часткових оцінок за порогами.
- Рішення: Часткова оцінка 100 у межах Warning, лінійне зниження до 0 на межі Critical; зважене середнє (T 0.30, CO₂ 0.30, RH 0.20, PM2.5 0.20); будь-яка критична метрика робить категорію «Некомфортно».
- Наслідки: Індекс узгоджений зі сповіщеннями і змінюється разом із порогами кімнати; формула проста для перевірки вручну (docs/analytics.md, 3.4). Ваги — продуктове рішення, винесені в конфігурацію.

## D-1-009 — Статистичні детектори аномалій замість ML

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Як виявляти несправності датчиків.
- Розглянуті варіанти: ML-модель (Isolation Forest); статичні межі; ковзний z-score + правила стрибка, завислого значення й пропуску.
- Рішення: Чотири статистичні детектори, O(n), параметри в конфігурації.
- Наслідки: Не потрібні дані для навчання, результат пояснюваний (z, швидкість зміни). Обробка σ = 0 через мінімальну значущу зміну ε. ML залишається можливим розширенням.

## D-1-010 — Підкреслення в назвах тестів

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Схема назв Method_Scenario_Expected порушує CA1707, а TreatWarningsAsErrors перетворює це на помилку збірки.
- Розглянуті варіанти: SuppressMessage на кожному тесті (як D-3-009); інша схема назв; вимкнення CA1707 лише для тестових проєктів.

## D-1-011 — Гістерезис і захист від спаму сповіщень

- Дата: 2026-10-12
- Автор: Учасник 1
- Проблема: Значення біля межі (1199 → 1201 → 1199 ppm) створювало б і закривало alert на кожному вимірі.
- Розглянуті варіанти: Новий alert на кожне перевищення; один відкритий alert на (кімната, метрика, рівень) і закриття після M нормальних вимірів поспіль.
- Рішення: Не більше одного відкритого alert-а того самого рівня (також частковий унікальний індекс у БД); закриття після 3 нормальних вимірів; Warning → Critical — ескалація.
- Наслідки: Клієнт не отримує потік однакових подій; поведінка перевіряється тест-кейсами AN-17…AN-20.
