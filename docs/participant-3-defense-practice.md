# Підготовка Учасника 3 до усного захисту

Це короткі опорні відповіді по власному коду. Офіційний банк із 400 питань не надано, тому цей документ не видається за його скорочений перелік. Вивчати варто причинно-наслідкові зв'язки й уміти відкрити відповідний файл.

## Пояснення своєї роботи за 60–90 секунд

«Моя частина — клієнт і інфраструктура перевірок. Client.Core містить HTTP-клієнт, сесію, ViewModels та підготовку даних, тому я можу тестувати цю логіку без телефону. Client.Maui відповідає за екрани, навігацію, захищене сховище та графік. Користувач входить, бачить кімнати й виміри, досліджує метрики за період, опрацьовує тривоги. Operator/Admin можуть змінювати пороги, Viewer — переглядати. SignalR повідомляє про зміну, а справжні дані клієнт перечитує через HTTP. Я також налаштував CI, платформні збірки, PostgreSQL smoke і документацію. Серверні формули й БД реалізували інші учасники. Для реалізації та перевірок використовував Codex, це задекларовано в META-USAGE».

Це текст для підготовки: перед захистом потрібно самостійно зрозуміти й показати кожну названу дію.

## 12 опорних питань по коду

1. **Навіщо два клієнтські проєкти?** Core не залежить від MAUI і тестується на Linux. MAUI реалізує платформні інтерфейси для навігації, Preferences та SecureStorage. Відкрити `MauiProgram.cs` і `INavigationService`.
2. **Як працює MVVM?** View відображає властивості ViewModel і викликає команди. ViewModel отримує API/навігацію через конструктор. Це дозволяє замінити HTTP і навігацію в тесті. Відкрити LoginPage.xaml та LoginViewModel.
3. **Де тут метапрограмування?** `[ObservableProperty]` генерує властивість і повідомлення про зміну, `[RelayCommand]` — команду. `ClientJsonContext` генерує JSON-метадані, `x:DataType` дає перевірку XAML bindings. Генератор скорочує повтори, але не гарантує правильності бізнес-поведінки.
4. **Що робить async/await?** HTTP очікується без блокування UI-потоку. Це не обов'язково створює новий потік. Стан сторінки змінюється в UI-потоці; callback SignalR проходить через PageLiveUpdates/MainThread.
5. **Навіщо CancellationToken?** При виході або зміні метрики старий запит більше не потрібний. Скасування зменшує зайву роботу, а version/context перевірка не дає пізній відповіді перезаписати нову. Відкрити RoomDetailsViewModel і ThresholdsViewModel.
6. **Що зберігається після login?** Access token, expiry, сервер і профіль; пароль і refresh token не зберігаються. SecureStorage має видимий memory-only fallback. Відкрити ClientSession та ClientPlatformServices.
7. **Чим різняться 401 і 403?** 401 означає, що сесія не прийнята: очищаємо її й повертаємо Login. 403 — чинний користувач не має права на дію: показуємо помилку, зберігаємо сесію й чернетку. UI-роль не замінює авторизацію API.
8. **Навіщо перевіряти адресу й redirect?** Токен прив'язаний до сервера. Remote адреса потребує HTTPS; HTTP дозволено лише локально. Redirect не повинен передати пароль/Bearer іншому origin. Є тести HTTP redirect та SignalR negotiation.
9. **Як працюють живі дані?** Підписки на кімнати й тривоги; подія позначає екран як такий, що потребує оновлення. HTTP refresh обмежено разом до одного за 5 с. Reconnect відновлює групи; без хаба polling кожні 30 с; logout припиняє канал. Відкрити ClientRealtime.
10. **Чому NoData не дорівнює 0?** Нуль може бути справжнім виміром або індексом комфорту. Порожні buckets розривають графік. Категорію комфорту повертає сервер; клієнт не дублює формулу. Відкрити AnalyticsPresentation і тести про gap/NoData.
11. **Що означають 168 тестів і 83.4%?** 168 — кількість виконаних тестів у solution; 67 із них клієнтські. 83.4% — покриття рядків Client.Core конкретним CI-запуском, не всього продукту й не нативного UI. Загальний звіт має 71.8%; показати artifact, а не називати 100%.
12. **Як перевірити зміну?** Спершу тест поведінки в Core, потім строгий build, відповідна MAUI-збірка й UI-прогін, якщо змінено екран. CI не замінює запуск на пристрої. Відкрити `.github/workflows/ci.yml`, TRX, coverage та static-analysis artifacts.

Для кожного питання: пояснити своїми словами → показати 10–20 рядків коду → назвати один реальний тест або сценарій. Якщо не пам'ятаєш деталь, знайди її у файлі й поясни, замість вигадувати.

## E2. Дві мікрозміни для тренування

Це заготовки, не нові вимоги продукту. Вносити в окремій тренувальній гілці/копії; поточний застосунок зберігає погоджену поведінку.

### 1. Додати період «14 днів»

- Файл: `src/Microclimate.Client.Core/ViewModels/RoomDetailsViewModel.cs`, колекція `Periods`.
- Зміна: між `new(7, "7 днів")` і `new(30, "30 днів")` додати `new(14, "14 днів")` та оновити пояснювальний коментар.
- Чому досить однієї зміни: Picker прив'язаний до Periods; `OnSelectedPeriodChanged` запускає refresh; `LoadAsync` обчислює `from = to.AddDays(-SelectedPeriod.Days)`. Для цього періоду використовується денне агрегування.
- Перевірка: вибрати 14 днів → початок діапазону має відрізнятися від кінця на 14 діб UTC; у запиті `interval=day`; одиниці й пороги не змінюються. Не використовувати `DateTime.Now` замість наявного TimeProvider.
- Пояснення на захисті: «Додаю значення в модель вибору. Обчислення й binding уже узагальнені за Days; серверний API змінювати не потрібно».

### 2. Відкривати сповіщення з фільтром «Відкриті»

- Файл: `src/Microclimate.Client.Core/ViewModels/AlertsViewModel.cs`, конструктор.
- Замінити `selectedStatus = Statuses[0]` на `selectedStatus = Statuses.Single(option => option.Value == AlertStatus.Open)`.
- Чому за значенням: перестановка пунктів Picker не повинна змінити семантику початкового фільтра. «Усі стани» лишається доступним користувачу.
- Перевірка: нова ViewModel → `InitializeAsync()` → HTTP query містить `status=open`; після вибору «Усі стани» й оновлення фільтр у query відсутній. Acknowledge і рольові обмеження не змінюються.
- Пояснення на захисті: «Змінюю тільки початковий вибір. Запит і пагінація вже використовують SelectedStatus та appliedStatus; після зміни фільтра список починається з першої сторінки».

```bash
dotnet test tests/Microclimate.Client.Tests -c Release --filter "FullyQualifiedName~ClientWorkflowTests|FullyQualifiedName~CompletionWorkflowTests|FullyQualifiedName~DefensePracticeTests"
```

Зелені наявні тести — перевірка відсутності регресій. Нову конкретну умову потрібно також перевірити сценарієм або цільовим тестом; саме додавання рядка в список не доводить правильності запиту.

## Перевірена тренувальна копія

15.11 обидві зміни застосовано в окремому чистому клоні. Додано два тести поведінки: точні 14 діб UTC з `interval=day` після автоматичного refresh; початковий `status=open` та відсутність status після вибору «Усі стани». Разом із ClientWorkflowTests і CompletionWorkflowTests пройшло **36/36**. Це репетиція коду, виконана Codex; особистий захист учасника ще не відбувся. Нативний UI саме цих навчальних змін не запускався.

```bash

cd ../mppSTEM-defense-practice
git apply --check docs/training/participant-3-microchanges.patch
```
