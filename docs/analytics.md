# Специфікація аналітики

Автор: Учасник 1. Статус: **чернетка Етапу 0**. Реалізація — Етап 2 (`Microclimate.Application/Analytics`), тести — за таблицею в розділі 7.

Документ описує, **що** і **як** рахує система: пороги за замовчуванням, агрегати, індекс комфорту, пошук аномалій і генерацію сповіщень. Позначка «[перевірити]» означає, що значення треба звірити з першоджерелом перед захистом; позначка «продуктове рішення» — що значення вибрано командою, а не взято з норми.

## 1. Пороги за замовчуванням

### 1.1. Семантика порогу

Для кожної метрики кімнати діє набір меж `CriticalMin ≤ WarningMin < WarningMax ≤ CriticalMax` (будь-яка межа може бути відсутня):

| Значення `v` | Стан |
|---|---|
| `WarningMin ≤ v ≤ WarningMax` | Норма |
| поза межами Warning, але в межах Critical | `Warning` |
| `v < CriticalMin` або `v > CriticalMax` | `Critical` |

Якщо Admin задав пороги кімнати (таблиця `Thresholds`), діють вони; інакше — значення за замовчуванням нижче (`Domain/Metrics/DefaultThresholds`).

### 1.2. Офіс, навчальна аудиторія, житлове приміщення (`Office`, `Classroom`, `Residential`, `Laboratory`, `Other`)

Відрізняються лише температура й вологість; інші метрики — як у 1.2 (шум і освітленість для серверної не оцінюються, вага 0).

|---|---|---|---|---|---|
| Температура, °C | 15 | 18 | 27 | 32 | ASHRAE TC 9.9 «Thermal Guidelines for Data Processing Environments»: рекомендований діапазон 18–27 °C, допустимий для класу A1 — 15–32 °C [перевірити редакцію] |
| Відносна вологість, % | 8 | 20 | 70 | 80 | ASHRAE TC 9.9, клас A1 (допустимий діапазон) [перевірити: у стандарті межі задано точкою роси] |

### 1.4. Обмеження підходу

- Норми ВООЗ для PM2.5 задано для усереднення за 24 години. Тому для PM2.5 поріг порівнюється не з окремим виміром, а з **ковзним середнім за 60 хв** (для решти метрик — з окремим значенням). Це компроміс між нормою і швидкістю реакції.
- Значення CO₂ за EN 16798-1 відносні (над зовнішнім повітрям); система не вимірює зовнішній CO₂, тому використовується припущення 400 ppm.

## 2. Агрегати

### 2.1. `Summary(room, metric?, range)`

Для кожної метрики (або однієї, якщо вказано): `min`, `max`, `avg`, `count`, `stdDev` (стандартне відхилення генеральної сукупності) за період `range = [from, to)`.

- Якщо вимірів немає — `count = 0`, інші поля `null`.
- Обчислюється однією SQL-командою `GROUP BY MetricType` (EF Core `GroupBy` + `Min/Max/Average/Count`). `stdDev` рахується через `avg(x²) − avg(x)²` в одному проході, бо стандартної функції немає в SQLite.

### 2.2. `Series(room, metric, range, interval)`

Часовий ряд агрегатів за кошиками `interval ∈ { Hour, Day }`:

- Межі кошиків — початок години/доби **в UTC** (`2026-10-12T14:00:00Z`).
- Для кожного кошика: `bucketStart`, `avg`, `min`, `max`, `count`.
- **Порожні кошики повертаються** з `count = 0` та `null` в агрегатах. Пропуски мають бути видимі на графіку клієнта, щоб не малювати пряму лінію через період, коли датчик не працював.
- Обмеження: `to − from ≤ 90 днів`; для `Hour` — не більше 31 дня (≤ 744 точок на графік).

Групування виконується **в БД**, порожні кошики додаються в пам'яті (їх ≤ 744). Перевірка, що запит транслюється в SQL, а не виконується в пам'яті: тест із `ToQueryString()` і логування EF Core на рівні `Information`.

### 2.3. Складність

`Summary` і `Series` — один прохід по індексу `IX_Measurements_Room_Metric_Time` (див. `docs/db-schema.md`): `O(k)`, де `k` — кількість вимірів за період, без сортування.

## 3. Індекс комфорту

### 3.1. Часткова оцінка метрики

Для поточного значення метрики `v` (середнє за останні **15 хв**) і порогів кімнати:

```
         ⎧ 100,                                    WarningMin ≤ v ≤ WarningMax
s(v) =   ⎨ 100 · (1 − d / D),                      v між межею Warning і межею Critical
         ⎩ 0,                                      v за межею Critical
```

де `d` — відстань від `v` до найближчої межі Warning, `D` — відстань між цією межею Warning і відповідною межею Critical. Якщо межі Critical з цього боку немає, `D = 20 %` від межі Warning (продуктове рішення).

Оцінка прив'язана до тих самих порогів, що й сповіщення: якщо Admin змінює пороги кімнати, індекс комфорту змінюється узгоджено.

### 3.2. Загальний індекс

```
CI = Σ wᵢ · sᵢ / Σ wᵢ      (сума лише за метриками, для яких є дані за 15 хв)
```

| Метрика | Вага `w` | Чому |
|---|---|---|
| Температура | 0.30 | Основний чинник теплового комфорту |
| CO₂ | 0.30 | Основний індикатор вентиляції, впливає на втому й концентрацію |
| Вологість | 0.20 | Впливає на тепловідчуття і слизові, але повільно |
| PM2.5 | 0.20 | Вплив на здоров'я, але рідше виходить за норму в приміщенні |
| Шум, освітленість | 0 (на Етапі 2) | Не всі датчики їх вимірюють; ввімкнення — конфігурацією |

Ваги — продуктове рішення команди; зберігаються в конфігурації, щоб їх можна було змінити без перекомпіляції.

### 3.3. Категорії

| CI | Категорія |
|---|---|
| ≥ 85 | Комфортно |
| 60–84.9 | Прийнятно |
| < 60 | Некомфортно |

Додаткове правило: якщо хоча б одна метрика має `s = 0` (стан `Critical`), категорія — **«Некомфортно»** незалежно від CI. Інакше середнє може «замаскувати» критичний CO₂ гарними іншими показниками.

### 3.4. Приклад розрахунку (кімната типу `Office`)

| Метрика | v | Межі | d | D | s | w | w·s |
|---|---|---|---|---|---|---|---|
| Температура | 25.5 °C | Warning ≤ 25, Critical ≤ 28 | 0.5 | 3 | 100 · (1 − 0.5/3) = **83.33** | 0.30 | 25.00 |
| Вологість | 35 % | Warning ≥ 40, Critical ≥ 20 | 5 | 20 | 100 · (1 − 5/20) = **75.00** | 0.20 | 15.00 |
| CO₂ | 1300 ppm | Warning ≤ 1200, Critical ≤ 1750 | 100 | 550 | 100 · (1 − 100/550) = **81.82** | 0.30 | 24.55 |
| PM2.5 | 8 µg/m³ | Warning ≤ 15 | 0 | — | **100** | 0.20 | 20.00 |

`CI = (25.00 + 15.00 + 24.55 + 20.00) / 1.00 = 84.55 ≈ 84.5` → **«Прийнятно»**.

### 3.5. Крайні випадки

| Ситуація | Результат |
|---|---|
| Немає даних за жодною метрикою за 15 хв | `CI = null`, категорія «Немає даних» (не 0 — відсутність даних ≠ погані умови) |
| Дані лише однієї метрики | CI = її `s` (формула з 3.2 нормує на суму наявних ваг) |
| Сума ваг наявних метрик = 0 | `CI = null` |
| Значення рівно на межі Warning | `s = 100` (межі включні) |
| Значення рівно на межі Critical | `s = 0` |

## 4. Пошук аномалій

Аномалія ≠ перевищення порогу. Поріг означає «погані умови в кімнаті»; аномалія — «дивна поведінка часового ряду», найчастіше несправність або збій датчика. Аномалії показуються на графіку і в звіті, але **не** створюють alert-ів на Етапі 2.

Усі детектори працюють з упорядкованим за `MeasuredAt` рядом одного датчика й однієї метрики, у пам'яті, за `O(n)`. Параметри — у конфігурації.

### 4.1. Викид (ковзний z-score)

- Вікно — `N = 30` попередніх **нормальних** точок (точки, вже позначені аномаліями, у вікно не потрапляють, щоб серія викидів не «перевчила» середнє).
- `μ`, `σ` — середнє і стандартне відхилення вікна; ведуться ковзними сумами `Σx` і `Σx²` → `O(1)` на точку.
- `z = (x − μ) / σ`; аномалія, якщо `|z| > 3`.
- Поки у вікні менше 10 точок — перевірка не виконується.
- Якщо `σ = 0` (усі значення вікна однакові), аномалія — якщо `|x − μ| > ε`, де `ε` — мінімальна значуща зміна метрики:

| Метрика | ε | Макс. швидкість зміни (4.2) |
|---|---|---|
| Температура | 0.5 °C | 2 °C/хв |
| Вологість | 2 % | 10 %/хв |
| CO₂ | 50 ppm | 500 ppm/хв |
| PM2.5 | 5 µg/m³ | 100 µg/m³/хв |
| Шум | 3 dB | — (шум легітимно змінюється різко) |
| Освітленість | 50 lux | — (вмикання світла) |

Значення `ε` і швидкостей — продуктове рішення на основі типової точності побутових датчиків.

**Приклад** (для наочності вікно `N = 5`): ряд температури `22.0, 22.1, 21.9, 22.0, 22.1, 25.0`.
Для точки `25.0`: `μ = 22.02`, `σ = √(((−0.02)² + 0.08² + (−0.12)² + (−0.02)² + 0.08²) / 5) = √0.0056 ≈ 0.0748`, `z = (25.0 − 22.02) / 0.0748 ≈ 39.8 > 3` → **викид**.

### 4.2. Різка зміна

`|xₖ − xₖ₋₁| / (tₖ − tₖ₋₁) > maxRate` для метрики (таблиця вище) → аномалія `Spike`. Наприклад, температура 22.0 → 26.5 °C за 1 хв (4.5 °C/хв > 2) — фізично неможливо для кімнати, ймовірно збій датчика.

### 4.3. «Завислий» датчик

Однакове значення (з точністю до `ε / 10`) `K = 120` разів поспіль → аномалія `Stuck` на всю серію. 120 точок при періоді 1 хв = 2 години: реальна кімната за цей час завжди хоч трохи змінюється.

### 4.4. Пропуск даних

`tₖ − tₖ₋₁ > 3 × очікуваний період` (період датчика — з конфігурації, за замовчуванням 60 с) → аномалія `Gap` з початком і кінцем пропуску.

### 4.5. Результат

```
Anomaly { Type: Outlier | Spike | Stuck | Gap, SensorId, Metric, From, To, Value?, Expected? (μ), Score? (z) }
```

Чому не ML-модель (Isolation Forest тощо): мало даних для навчання на старті, результат важко пояснити користувачу і на захисті, а прості статистичні правила покривають основні несправності датчиків. ML — можливе розширення.

## 5. Генерація сповіщень

При інгесті кожного виміру (в одній транзакції з його збереженням, див. `docs/db-schema.md`, розділ 4):

1. Знайти пороги кімнати для метрики (або значення за замовчуванням).
2. `level = Threshold.Evaluate(v)` → `null` / `Warning` / `Critical`.
3. Якщо `level ≠ null`:
   - якщо для `(RoomId, MetricType)` вже є **відкритий** alert того самого рівня — нічого не створювати (захист від спаму; гарантується також частковим унікальним індексом `UX_Alerts_Open`);
   - якщо відкритий alert рівня `Warning`, а новий рівень `Critical` — створити `Critical` (ескалація), `Warning` закрити як `Resolved`;
   - інакше — створити `Alert(Open)`.
4. Якщо `level = null` і є відкритий alert — **гістерезис**: alert переходить у `Resolved` лише після `M = 3` вимірів поспіль у нормі. Без гістерезису значення, що «тремтить» біля межі (1199 → 1201 → 1199 ppm), створювало б і закривало alert на кожному вимірі.
5. Після фіксації транзакції — `IAlertNotifier.AlertRaisedAsync` / `AlertResolvedAsync` (реалізація через SignalR — Учасник 2). Сповіщення відправляються **після** commit, щоб клієнт не отримав подію про alert, якого немає в БД.
