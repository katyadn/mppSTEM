# Симулятор датчиків

Автор: Учасник 1. Статус: **дизайн Етапу 0**, реалізація — Етап 2 (`src/Microclimate.SensorSimulator`).

## 1. Призначення

Реальних датчиків у команди немає, тому симулятор генерує правдоподібні виміри для:
- демонстрації системи (Dashboard, графіки, сповіщення в реальному часі);
- навантажувальних тестів (JMeter / велика кількість віртуальних датчиків);
- наскрізної перевірки аналітики: кожен сценарій з розділу 3 має давати **передбачуваний** результат (alert або аномалію).

## 2. Модель сигналу

Для кожної метрики значення в момент `t` (години від початку доби, UTC + зсув кімнати):

```
x(t) = base + A · sin(2π · (t − φ) / 24) + occupancyEffect(t) + noise,   noise ~ N(0, σ²)
```

| Метрика | base | A (добова амплітуда) | φ (пік, год) | σ (шум) | Особливості |
|---|---|---|---|---|---|
| Температура, °C | 22.0 | 1.5 | 15 | 0.1 | +0.5 °C під час зайнятості кімнати |
| Вологість, % | 45 | 5 | 5 | 0.5 | Слабка обернена кореляція з температурою: −1.5 % на +1 °C відхилення від base |
| CO₂, ppm | 450 | 0 | — | 15 | Див. модель зайнятості нижче |
| PM2.5, µg/m³ | 6 | 2 | 19 | 0.8 | Значення обрізаються знизу нулем |
| Шум, dB(A) | 35 | 0 | — | 2 | +12 dB під час зайнятості |
| Освітленість, lux | 50 | 0 | — | 10 | 450 lux під час робочих годин (увімкнене світло) |

**Модель зайнятості для CO₂** (робочі години за замовчуванням 09:00–18:00, будні):
- під час зайнятості: `CO₂ += k_in · people · Δt − k_vent · (CO₂ − 420) · Δt` — накопичення від людей і виведення вентиляцією;
- поза зайнятістю: лише вентиляція, експоненційний спад до ≈ 420 ppm.
Параметри `people`, `k_in`, `k_vent` задаються для кімнати; за замовчуванням підібрані так, що без вентиляційних проблем CO₂ стабілізується близько 900–1000 ppm.

Значення обрізаються до фізичних меж (`MetricLimits` у домені) і округлюються до роздільної здатності типового датчика (T — 0.1 °C, RH — 1 %, CO₂ — 1 ppm).

## 3. Сценарії

Сценарій задається для кімнати (або окремого датчика) і накладається на модель з розділу 2.

| Сценарій | Що відбувається | Очікувана реакція системи |
|---|---|---|
| `normal` | Тільки модель з розділу 2 | Жодних alert-ів і аномалій |
| `overheat` | Температура зростає на +0.1 °C/хв до 29 °C, тримається 30 хв, повертається | `Warning` при > 25 °C → `Critical` при > 28 °C → `Resolved` після 3 нормальних вимірів |
| `poor-ventilation` | `k_vent` зменшено в 4 рази | CO₂ > 1200 → `Warning`, > 1750 → `Critical` |
| `spike` | З імовірністю 0.5 % на вимір — викид ±5σ…±10σ | Аномалія `Outlier`; при різкій зміні температури — `Spike` |
| `stuck-sensor` | Через 10 хв датчик постійно надсилає останнє значення | Аномалія `Stuck` через 120 вимірів |
| `offline` | Датчик мовчить 10 хв, потім відновлюється | Аномалія `Gap`; буфер датчика досилає пропущені виміри (див. 5) |
| `dry-winter` | Вологість base = 22 % | `Warning` за вологістю (< 40 %), без `Critical` |

## 4. Конфігурація (`appsettings.json`)

```json
{
  "Simulator": {
    "ApiBaseUrl": "https://localhost:7001",
    "Mode": "Api",
    "OutputDirectory": "./simulated",
    "Seed": 42,
    "MeasurementPeriod": "00:01:00",
    "BatchSize": 10,
    "TimeAcceleration": 1,
    "Rooms": [
      {
        "RoomId": "00000000-0000-0000-0000-000000000000",
        "Scenario": "normal",
        "People": 6,
        "Sensors": [
          {
            "SensorId": "00000000-0000-0000-0000-000000000000",
            "DeviceKey": "з user-secrets або змінної середовища",
            "Metrics": [ "Temperature", "Humidity", "Co2" ]
          }
        ]
      }
    ]
  }
}
```

- `Seed` — фіксує генератор випадкових чисел: однаковий seed → однакові дані. Потрібно для відтворюваних тестів і демонстрацій.
- `TimeAcceleration` — множник часу симуляції (наприклад, 60: одна хвилина реального часу = година симуляції) для швидкої демонстрації добових циклів.
- Device key **не зберігається** в `appsettings.json` у git — лише user-secrets або змінні середовища.

## 5. Конкурентність і надійність

- Кожен датчик — окремий асинхронний цикл (`Task`) з `PeriodicTimer`. Сотні датчиків не потребують сотень потоків: цикли чекають асинхронно і використовують пул потоків лише на час генерації та відправки.
  - Чому не `Thread`: дорогий ресурс (≈ 1 МБ стеку), не масштабується до сотень датчиків.
  - Чому не `System.Timers.Timer`: callback-и можуть перекриватися при повільній відповіді API, складніша коректна зупинка.
- Генератор випадкових чисел — окремий `Random(seed + sensorIndex)` на датчик: `Random` не потокобезпечний, а окремий seed зберігає відтворюваність.
- `HttpClient` — через `IHttpClientFactory` (типізований клієнт), щоб уникнути вичерпання сокетів.
- Зупинка — через `CancellationToken` від `BackgroundService.ExecuteAsync`; при зупинці буфер намагається відправитися ще раз.
- **Повтори:** при мережевій помилці або `5xx` — до 5 спроб з експоненційною затримкою (1, 2, 4, 8, 16 с) з випадковим зсувом; при `4xx` — не повторювати, логувати (помилка даних або ключа).
- **Буфер:** поки API недоступне, виміри накопичуються в черзі (до 1000 на датчик, далі найстаріші відкидаються) і досилаються пакетами після відновлення. Повторна відправка безпечна завдяки ідемпотентності на боці БД (UNIQUE `SensorId, MetricType, MeasuredAt`).

## 6. Взаємодія з API

- `POST /api/v1/measurements` із заголовком `X-Device-Key` (формат запиту `MeasurementBatchRequest` з `Microclimate.Contracts`; деталі — у `docs/api.md` Учасника 2).
- Очікувана відповідь — `202 Accepted`; `400` — пакет відхилено повністю (логувати тіло ProblemDetails); `401` — неправильний ключ (зупинити датчик, щоб не спамити).

## 7. Режим без API

`Mode = "Csv"`: виміри записуються у файли `OutputDirectory/<roomId>.csv` у форматі імпорту:

```csv
sensorId,metric,value,measuredAt
3f2c...,Temperature,22.4,2026-10-12T14:30:00Z
```

Використання: генерація тестових наборів для імпорту (`POST /rooms/{id}/measurements/import`), unit-тести аналітики на «реалістичних» даних, демо без запущеного API.

## 8. Логування і метрики

- Структуровані логи: старт/зупинка датчика, помилки відправки, розмір буфера.
- Метрики (OpenTelemetry, інтеграцію налаштовує Учасник 2 / Учасник 3 у Compose): кількість відправлених вимірів, кількість помилок, розмір буфера.
