# Модель безпеки та контролю доступу (docs/security.md)

Цей документ визначає політику безпеки, автентифікацію, авторизацію, розподіл ролей, захист від атак та правила роботи з секретами в системі Microclimate.

---

## 1. Ролі користувачів та акторів системи

У системі визначено чотири ролі (три людські та одна апаратна):
1. **Admin (Адміністратор):** Повний доступ до системи: управління користувачами та їхніми ролями, реєстрація будівель, приміщень і сенсорів, ротація ключів пристроїв, налаштування граничних порогів, квитування сповіщень та аналітика.
2. **Operator (Оператор):** Експлуатаційний персонал: моніторинг показників, коригування граничних порогів кімнат, підтвердження (acknowledge) сповіщень про інциденти, імпорт та експорт історичних даних.
3. **Viewer (Спостерігач):** Звичайний користувач приміщень: перегляд поточного стану мікроклімату, графіків та аналітики приміщень, списку сповіщень (без можливості зміни даних, порогів або квитування).
4. **Device (Апаратний сенсор / Симулятор):** Автономний пристрій або процес-симулятор: надсилання пакетних вимірів мікроклімату через захищений заголовок пристрою без людського контексту.

## 3. Автентифікація користувачів (JWT + Refresh Tokens)

### 3.1. Access Token (JWT)
- **Алгоритм підпису:** `HMAC-SHA256` (`HS256`).
- **Секретний ключ:** Мінімальна довжина 256 біт (32 байти). Отримується виключно з конфігурації / змінних середовища `Jwt:SecretKey` (або `user-secrets` під час локальної розробки). Заборонено хардкодити в коді.
- **Термін дії (TTL):** **15 хвилин**. Короткий життєвий цикл мінімізує шкоду у випадку викрадення токена.
- **Обов'язкові Claims у токені:**
  - `sub`: ідентифікатор користувача (`Guid`).
  - `email`: адреса електронної пошти користувача.
  - `role`: назва ролі (`Admin`, `Operator`, `Viewer`).
  - `jti`: унікальний ідентифікатор токена (UUID v4) для запобігання повторним атакам (replay attack).
  - `iss`: `"Microclimate.Api"`.
  - `aud`: `"Microclimate.Client"`.

### 3.2. Refresh Token та політика ротації
- **Формат:** Криптографічно стійка псевдовипадкова послідовність 64 байтів (`RandomNumberGenerator.GetBytes(64)`), закодована в Base64.
- **Термін дії (TTL):** **7 діб** від моменту створення.
- **Збереження в БД:** Відкритий refresh-токен повертається клієнту один раз і **ніколи не зберігається у базі даних у відкритому вигляді**. У таблиці `RefreshTokens` зберігається лише його SHA-256 хеш (`TokenHash`).
- **Ротація токенів (Token Rotation):**
  - При кожному зверненні на `/api/v1/auth/refresh` наданий refresh-токен **одноразово споживається та анулюється** (`RevokedAt = DateTimeOffset.UtcNow`).
  - Генерується повністю нова пара (Access Token + Refresh Token).
  - У БД записується хеш нового токена в поле `ReplacedByHash`.
- **Виявлення компрометації (Reuse Detection):**
  - Якщо сервер отримує refresh-токен, який вже був раніше відкликаний (`RevokedAt != null`), це свідчить про спробу перехоплення старого токена зловмисником.
  - У такому разі **негайно відкликаються всі активні refresh-токени цього користувача** (ланцюжок сесій анулюється), повертається `401 Unauthorized`, і користувач зобов'язаний заново ввести логін і пароль.

> **Залежність від Учасника 1:**
> Для реалізації цієї моделі Учасник 1 має створити сутність `RefreshToken` у шарі `Domain` та відповідну таблицю в EF Core:
> `UserId (Guid)`, `TokenHash (string)`, `ExpiresAt (DateTimeOffset)`, `CreatedAt (DateTimeOffset)`, `RevokedAt (DateTimeOffset?)`, `ReplacedByHash (string?)`.

## 4. Зберігання паролів

- Для хешування паролів використовується `Microsoft.AspNetCore.Identity.PasswordHasher<TUser>` (алгоритм PBKDF2 з HMAC-SHA512, 100 000 ітерацій, випадкова 128-бітна сіль).
- **Чому не повноцінний ASP.NET Core Identity:** Повний ASP.NET Core Identity приносить важкі таблиці (Claims, Logins, Roles, UserTokens), прив'язку до специфічних UI-шаблонів та надлишкову складність. У нашій архітектурі достатньо легковісної сутності `User` з хешем і роллю.
- **Вимоги до пароля (валідація при створенні):**
  - Мінімальна довжина: **8 символів**.
  - Обов'язкова наявність щонайменше однієї великої літери, однієї малої літери та однієї цифри.

## 5. Автентифікація сенсорів (`X-Device-Key`)

- Апаратні датчики та процеси симулятора не мають облікового запису користувача, пароля та контексту браузерної сесії. Використання JWT для них є надлишковим (немає потреби у ролях чи refresh-токенах).
- Автентифікація здійснюється через HTTP-заголовок `X-Device-Key: <RawKey>`.
- **Генерація та збереження:**
  - Ключ сенсора — криптографічно безпечний рядок з 32 байтів (64 символи hex або 44 base64).
  - При створенні сенсора (`POST /api/v1/sensors`) або ротації (`POST /api/v1/sensors/{id}/rotate-key`) ключ показується **одноразово** у відповіді `SensorCreatedResponse`.
  - У БД сутність `Sensor` зберігає лише `DeviceKeyHash` (SHA-256 хеш ключа з сіллю).
  - При надходженні запиту на `/measurements` Api хешує переданий `X-Device-Key` і порівнює з `DeviceKeyHash` у базі даних (із використанням константного за часом порівняння `CryptographicOperations.FixedTimeEquals` проти timing attacks).

## 6. Політика CORS (Cross-Origin Resource Sharing)

- CORS налаштовується в `Program.cs` через `AddCors` з отриманням дозволених джерел із конфігурації:
  ```json
  "Cors": {
    "AllowedOrigins": [
      "http://localhost:5173",
      "https://localhost:5001"
    ]
  }
  ```
- **Чому нативному MAUI-клієнту не потрібен CORS:**
  CORS є виключно механізмом безпеки веб-браузерів (Same-Origin Policy), який обмежує запити, що надсилаються сценаріями JavaScript між різними origin. Нативні застосунки (Android, iOS, Windows/macOS у .NET MAUI) виконують мережеві HTTP-запити через нативні системні сокети без браузерної пісочниці, тому CORS до них не застосовується. CORS у нашому API потрібен для:
  - Swagger UI / OpenAPI документації в браузері.
  - Автоматизованих інтеграційних JS-тестів або потенційного веб-клієнта (SPA/Blazor).

## 7. Зовнішній вхід (OAuth 2.0 / OpenID Connect)

- Зовнішня автентифікація через сторонніх провайдерів (Google Workspace, Microsoft Entra ID) запланована на **Етап 2**.
- **Архітектурна інтеграція з поточною моделлю:**
  - Клієнт проходить OAuth 2.0 Authorization Code Flow з PKCE у провайдера і надсилає отриманий ID Token на `POST /api/v1/auth/external-login`.
  - API валідує токен провайдера, витягує email користувача.
  - Якщо користувач з таким email існує у БД, система генерує стандартний внутрішній JWT access-токен і refresh-токен Microclimate.
  - Таким чином вся подальша авторизація та матриця прав залишаються незмінними.

## 8. Управління секретами

- **Локальна розробка:** Секретні ключі JWT, паролі баз даних зберігаються через механізм `dotnet user-secrets` у сховищі розробника (`secrets.json`), що розташоване за межами дерева вихідного коду git.
- **CI / Docker / Production:** Секрети передаються через захищені змінні середовища контейнера або GitHub Actions Secrets (наприклад, `JWT__SECRETKEY`, `CONNECTIONSTRINGS__DEFAULTCONNECTION`).
- У файл `appsettings.json` та `appsettings.Development.json`, що додаються в git, дозволено записувати **виключно публічні або некритичні значення за замовчуванням**. Будь-який компрометуючий секрет у git суворо заборонений.

## 9. Додаткові заходи безпеки

1. **HTTPS Enforced:** Усі комунікації з API відбуваються через TLS 1.3/1.2 (`UseHttpsRedirection`, HSTS).
2. **Обмеження розміру запитів:**
   - Для пакетів `/measurements` введено жорстке обмеження кількості вимірів: максимум 500 записів за один запит.
   - Для імпорту CSV-файлів введено обмеження розміру тіла запиту до 10 МБ (`[RequestSizeLimit(10 * 1024 * 1024)]`).
3. **Захист від Brute-Force та DoS (Етап 2):** Впровадження Rate Limiting (`System.Threading.RateLimiting`) для публічних ендпоінтів `/auth/login` та `/auth/refresh` (наприклад, не більше 5 спроб на хвилину з однієї IP-адреси).
